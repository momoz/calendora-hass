# Calendora — third-party API contract

This is the **entire** interface available to this integration. If something you need is not
in this document, it is not part of the contract — **file a gap with the maintainer.** Do
not infer endpoints, do not probe, do not use anything you find that is not written here.

---

## 1. Conventions

**Envelope**
```
{ "ok": true,  ...data }
{ "ok": false, "error": "..." }
```

**Status codes.** The code lives on the failure, not on the route — the same condition
answers the same way everywhere.

| | |
|---|---|
| 400 | malformed request, or an unknown / non-writable field (see §5) |
| 401 | unauthenticated |
| 404 | not found — **also returned for "not yours"**, so the endpoint cannot be used to test whether an id exists |
| 409 | conflict |
| 426 | unsupported API version |

**Membership is verified per request.** A household id in a query string is a request, not a
claim.

**Timezones are binding.** Every timestamp carries its zone. All-day events and birthdays
are **date-only** and must never be converted to instants — a birthday that shifts a day is
a data bug, not a display bug.

## 2. Phase 1 — the calendar feed (available now, no auth)

```
GET /api/feeds/{token}
GET /api/feeds/{token}?member={memberId}
```

Returns **iCalendar (ICS)**.

The token is a **capability URL** — possession is authorisation. It is session-free by
necessity: Apple and Google fetch subscribed calendars from their own servers with no
cookies. The user supplies it during config flow; it is off until they turn it on and is
revoked by regenerating.

- Treat the token as a **secret**. Never log it, never put it in a diagnostics dump, never
  include it in an issue template.
- `?member=` narrows to one person.
- The ICS carries `RRULE`s. **You must expand them** — Home Assistant's `async_get_events`
  requires expanded occurrences, not master rules.
- Read-only. There is no write path here, and there will not be one.

**This endpoint is Phase 1 only.** Once `/api/v1` ships, using the feed for anything is a
workaround and a contract violation.

## 3. Authentication (Phase 2 onward)

```
Authorization: Bearer <api-key>
```

Keys are issued by the user in Calendora settings, scoped to **one household**, and
revocable. Scopes, and there is no wildcard:

`calendar:read` · `calendar:write` · `lists:read` · `lists:write` · `household:read` ·
`presence:write`

A revoked or invalid key returns **401**. Raise `ConfigEntryAuthFailed` so Home Assistant
starts a reauth flow — never fail silently, never retry a 401.

**A key is not a member.** Changes made with it are attributed to the integration, never to
a person. Nothing you create carries a member's colour or appears authored by them.

## 4. `/api/v1`

Versioned independently of anything else. **Additive only** — new endpoints and new optional
fields; a breaking change becomes `/api/v2` with v1 kept alive for at least one release.

Declare the version you target. If the server answers **426**, fail loudly **once** with a
clear repair message. Never degrade silently and never fall back to another surface.

```
GET    /api/v1/household
GET    /api/v1/members
GET    /api/v1/people

GET    /api/v1/events?from=&to=&member=      # occurrences, recurrence already expanded
POST   /api/v1/events
PATCH  /api/v1/events/{id}                    # ?scope=this|following|all
DELETE /api/v1/events/{id}                    # ?scope=this|following|all

GET    /api/v1/lists
GET    /api/v1/lists/{id}/items
POST   /api/v1/lists/{id}/items
PATCH  /api/v1/lists/{id}/items/{itemId}
DELETE /api/v1/lists/{id}/items/{itemId}

POST   /api/v1/presence
GET    /api/v1/events/{id}/leave-by

GET    /api/v1/stream                          # SSE
```

**`GET /api/v1/events` returns expanded occurrences.** The server does the expansion — do
not re-derive it.

**`scope` is required when mutating a recurring event.** `this` | `following` | `all`.
There is no default, deliberately: a silent choice here destroys data. If the user's intent
is unknown, ask or refuse — do not guess.

**`GET /api/v1/stream`** is Server-Sent Events with a **deliberately empty payload**: it
means *something changed, pull again*. Do not expect rows on it. Use it to drive
`coordinator.async_set_updated_data()`; keep a slow poll only as a fallback.

## 5. Unknown fields are rejected, not ignored

Send a field that is unknown or not writable and you get **400 naming the field**.

This is deliberate and differs from Calendora's internal protocol, which silently drops
them. A silent drop is invisible to a third party — it looks like a successful save, and the
user reports it against the wrong project. Loud is correct here.

Consequence: **do not send fields speculatively.** Send what the endpoint documents.

## 6. `POST /api/v1/presence` — do not build without explicit approval

```
POST /api/v1/presence
{ memberId, at, kind: "arrived"|"departed", place: {lat, lon, accuracy} | {zone: "..."} }
```

Location-verified attendance: a member observed at an event's place during its window
resolves that event without giving events a done state.

**This is the most sensitive data Calendora will ever hold — a location history of a
family.** Retention, whether it syncs to devices, and per-member opt-out are unmade product
decisions. Building this before they are made is a contract violation, not initiative.

---

## 7. Not available, and not coming

Do not ask for, infer, probe for, or build against:

- **The sync protocol.** First-party clients only. It is replication, not an API, and it is
  explicitly out of bounds.
- **Identity** — sessions, passkeys, invitation tokens. These do not even reach a browser's
  local storage.
- **Impersonation and support tooling.**
- **The personal Second Brain.** Private is a *retrieval* rule; a third-party API is a
  retrieval path. No scope grants it, now or ever.
- **The household activity log.** Server-only by design and never synced. There is currently
  no JSON route for the household-level view — if you need it, **file a gap. Do not scrape
  the HTML.**

---

## 8. Security expectations of this integration

- The API key and the feed token are secrets. Not in logs, not in diagnostics, not in issue
  templates, not in debug output.
- Redact both from any config-entry diagnostics you implement.
- The Home Assistant webhook id, if you register one, **is itself a credential** — generate
  it with `webhook.async_generate_id()` and never derive it from a household id, a user id,
  or anything else guessable.
- No real household data in screenshots, test fixtures, or example YAML in this public repo.
